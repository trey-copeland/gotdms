# File status, torn tails, and Follow

[Back to the docs index](README.md)

## File status and `WithLenientTail`

`File.Status` reports whether the file ended on a finished segment, on the NI incomplete-segment sentinel (`0xFFFFFFFFFFFFFFFF` in the next-segment offset), or on a truncated tail recovered by `WithLenientTail`. `PartialTail` is set when that segment's raw bytes do not end on a chunk boundary. `UnusedTail` is the number of leftover raw bytes that were not a whole value. `Open` of a well-formed file is unchanged. `Open` of an incomplete file is also unchanged: `Values` still returns every whole value in the tail. A next-segment offset that runs past EOF returns `ErrTruncated` unless `WithLenientTail` is set. With that option the earlier segments open, whole values in the partial tail are readable, and `Status` reports `Truncated`. Those tail samples are not committed. A trailing fragment shorter than a lead-in, a final segment whose metadata itself runs past EOF, or bytes after the last whole segment that do not parse at all (zeros, garbage) are a torn tail. A strict `Open` returns its error. With `WithLenientTail` the torn bytes are dropped: `Truncated` is set, `DroppedTail` is their length, and `TailError` is the strict error. Truncating the file to its size minus `DroppedTail` makes it open strictly. A segment whose lead-in declares a finite length inside the file was published after its bytes, so an error inside it is corruption and is returned even with the option, as is `ErrUnsupported` anywhere. The reader cannot tell an unreadable lead-in (zeros, a bad tag) in the middle of a file from a torn one, so that still ends a lenient file there; check `DroppedTail` before truncating. A file with no whole segment, and an I/O error, still fail with the option. A file `Open` rejects has no `FileStatus`. `dataset.WithLenientTail` applies the option to indexing and reads, and `Dataset.FileStatus` reports each file's status.

`ExampleWithLenientTail` opens a torn file, reads `DroppedTail`, truncates it, and opens it strictly. How a `WithSync` writer limits a power loss to a torn tail is in [Writing](writing.md#crash-safety-and-durable-writes-withsync). The `gotdms info --lenient` output is in [CLI](cli.md). Datasets take the same option; see [Datasets](dataset.md#torn-files-and-the-segment-index).

## Follow

`Follow` is for a file another process is still writing. It polls at `WithTailInterval` (default 100 ms) and returns batches of at most `WithTailBatch` samples (default 4096). It opens with `WithLenientTail`. Samples come from segments whose next-segment offset is a real length and whose bytes are fully present. A segment that still carries the sentinel is skipped, including whole values already flushed into it. A final segment whose finite length runs past EOF is also skipped until a later poll sees those bytes. A missing file is treated as "not finished yet" and polled again. A torn tail whose strict error is `ErrTruncated` (a short trailing lead-in, or metadata past EOF) is too: the whole segments before it are delivered, and the next poll may see that segment finished. `Follow` cannot tell a writer that is still running from one that stopped, so on a file that will never grow it waits until the context is cancelled. A torn tail of another kind (zeros, a bad tag, garbage) stops the tail with that error, as does any other error. Cancel the context to stop; `Err` is that context error. `Close` unblocks `Next` and leaves `Err` nil. The channel is selected by group name and channel name. A channel named `Time` is returned in its stored type.
